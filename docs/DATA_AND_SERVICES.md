# Student OS — Data & Services

> This document describes the **future data categories** and **external service boundaries** for Student OS. It is a **blueprint** of where data lives and which services may be used. **No integrations, credentials, or actual connections are implemented.**

## Purpose

Define a clear map of:
1. What data the platform stores and where it lives.
2. Which external services may back the platform (free-tier-friendly).
3. Boundaries between local, cloud, and third-party concerns.

No implementation credentials or actual integrations appear here.

## Data Categories

Data is classified by owner and sensitivity. All categories follow the privacy commitments in [PROJECT_VISION.md](./PROJECT_VISION.md) and [USER_SYSTEM.md](./USER_SYSTEM.md).

### 1. Account & Identity Data
- Authentication identity, role, account lifecycle state.
- Sensitive; guarded by backend auth and access control.

### 2. Student Profile & Preferences
- Profile fields, educational path context, appearance, notification, and privacy preferences.
- Owned by the student; used for personalization only.

### 3. Student Content
- Planning, study, preparation, milestone, exam, resource, wellbeing, notes and progress data generated by the student.
- Owned by the student; the core value of the platform.

### 4. Community / Social Data
- Study circles, discussions, shared achievements.
- Opt-in; governed by moderation (see [ADMIN_SYSTEM.md](./ADMIN_SYSTEM.md)).

### 5. Reward & Gamification Data
- Points, badges, streaks, achievement records.

### 6. Platform / Content Data
- Admin notices, announcements, banners, campaigns, templates, reward catalogs.
- Created/scheduled by administrators or automation.

### 7. Configuration & Feature Flags
- Feature flags, thresholds, platform configuration.

### 8. Analytics & Telemetry
- Aggregated platform metrics (active users, feature adoption).
- Privacy-respecting; no invasive individual tracking by default.

### 9. Audit Data
- Admin action logs and key lifecycle events (append-only).

## Data Storage Model

### Remote Persistence (Backend Database)
- Relational storage (PostgreSQL) for structured data across all categories above.
- Primary candidate: **Supabase** as the managed backend.

### Local Storage / Cache
- Local cache for offline access and fast startup.
- Local preference and session cache on-device.
- Local store for data that never needs to leave the device (where privacy benefits).

### Media / Content Delivery
- File/asset storage for uploads (avatars, resources, media) with a CDN-backed delivery boundary.
- Primary candidate: Supabase Storage (free-tier) where appropriate.

## External Service Boundaries

The platform may use the following categories of free-tier-friendly services. Boundaries keep responsibilities clear and avoid lock-in.

### Authentication & Database / Backend
- **Boundary:** account identity, relational persistence, server-side logic.
- **Candidate:** Supabase (Auth + Postgres + Edge Functions).
- Rules: never hard-code credentials; credentials live in secure environment configuration.

### Realtime
- **Boundary:** live sync and subscriptions for collaborative/community features.
- **Candidate:** Supabase Realtime.

### Notifications
- **Boundary:** scheduled and in-app notifications to students.
- **Approach:** in-app/local notifications first; free-tier push where available and appropriate.
- Never use notifications for intrusive advertising.

### Analytics
- **Boundary:** aggregated, privacy-respecting platform metrics.
- **Candidate:** free-tier analytics opted-in by default off; aggregated only.

### Media / Content Delivery
- **Boundary:** serving user-uploaded and platform content efficiently.
- **Candidate:** Supabase Storage with CDN, or other free-tier CDN when justified.

### Authentication of Third-Party Identity (future optional)
- **Boundary:** social/OAuth sign-in.
- **Candidate:** OAuth via backend provider; never store third-party secrets in the app.

## Service Selection Guidelines

1. Prefer **free/open-source** and free-tier solutions.
2. Keep **boundaries** explicit so a service can be swapped without architectural change.
3. **One concern per service** — avoid a service owning unrelated concerns.
4. Never add a dependency without a clear need (see [DEVELOPMENT_RULES.md](./DEVELOPMENT_RULES.md)).
5. Store **no secrets** in source or commits.

## Security & Privacy Cross-Cutting

- Access control (Row Level Security in Postgres) scopes users to their own data.
- Student data ownership and an export/delete path (see [USER_SYSTEM.md](./USER_SYSTEM.md)).
- Audit logging for admin actions (see [ADMIN_SYSTEM.md](./ADMIN_SYSTEM.md)).

## Non-Goals (for now)
- **No** actual integrations, API keys, or database connections.
- **No** database tables created.
- Implementation begins in later phases per [ROADMAP.md](./ROADMAP.md).
